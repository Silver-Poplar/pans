# 02 断言宏与测试骨架

这次提交四块：pans 的第一个公开头 `macros.h`（类型别名、边界常量、一组断言宏），一个自检用例 `test_macros.cpp`，把 `tests/CMakeLists.txt` 从空文件变成能自动收用例的构建规则，以及 `.gitignore` 补一条。

## pans/include/pans/macros.h

第一个公开头，放在 `pans/include/pans/` 下，之后包含方式是 `<pans/macros.h>`。头文件守卫用路径式命名 `PANS_INCLUDE_PANS_MACROS_H`，省得跟别处撞。

### 类型别名与常量

`u8/s8` 一路到 `u64/s64`，用 `using` 挂在全局，省掉 `uint32_t` 这种啰嗦写法。

`INVALID8/16/32/64` 和 `MAX_U8/.../MAX_U64` 现在取的是同一批值（全 1），也就是"无效值"直接拿无符号最大值当哨兵。用例里有 static_assert 把这两组绑死，以后谁改掉其中一个都会被编译期拦下。

类型上有个不对称：8/16/32 位那几对都是字面量，落到 `int` 或 `unsigned int`；只有 64 位那两个写成 `~0ULL`。比较值没错，但推导出的类型不一致，将来做模板推导或者传 `printf` 时要注意。

### 断言宏

全部建立在两个基础宏上：

- `PANS_ASSERT(x)`：条件不成立就往 stderr 打 `文件:行号` 加原始表达式字符串，然后调 `assert(x)`。分支挂 `[[unlikely]]`
- `PANS_ASSERT2(x, w)`：多一个 `w`，能塞任意可 `<<` 的东西当上下文，比如循环下标

上面再包一层，按"失败之后干什么"分成五类，命名是 `ASSERT_<动作>[2]`：

- `RETVAL(x, val)` 返回 `val`，`RETNONE(x)` 直接返回，`NOEFFECT(x)` 什么都不做继续往下——这三个用 `do{...}while(0)`
- `CONTINUE(x)` 走 `continue`，`BREAK(x)` 走 `break`——这两个展开成 `if(!x){...}else{}`

两类实现方式不同是有原因的：`do{...}while(0)` 里不能放 `break` / `continue` 去影响外层循环，那个 `break` 只会跳出 `do-while` 自己。所以 CONTINUE/BREAK 必须展开成真正的 `if`，末尾补个 `else{}` 让它能安全地当一条语句加分号。RETVAL 那几个用 `do{...}while(0)` 是标准做法，保证宏跟在 `if` 后面不加花括号也不会断。里面那句 `if(x) [[likely]] break;` 是提前跳出 `do-while`、跳过后面的 `PANS_ASSERT`，正常路径不产生额外开销。

### 一个要注意的行为

`PANS_ASSERT` 里那段 stderr 打印没有用 `NDEBUG` 包起来，随 `NDEBUG` 失效的只有 `assert(x)`。所以 Release 下一个失败的断言会照常刷诊断信息，但程序继续跑——诊断和终止是解耦的。这一点在下面的实测里能直接看到。

打印格式里 `__LINE__` 后面直接拼 `"ASSERTION FAILED"`，中间少了个分隔符，出来是 `test_macros.cpp:63ASSERTION FAILED`；`PANS_ASSERT2` 那条是 `Assert ... failed`，两边格式没对齐。

## tests/test_macros.cpp

不依赖任何测试框架，`main` 直接跑，靠退出码说话。分两块：

- 编译期：static_assert 检查 8 个类型别名的宽度和符号性，以及两组常量跟 `std::numeric_limits` 是否一致
- 运行期：把每个断言宏都实际触发一遍，用 `cout` 打标记看控制流走到哪

第二块是重点，验的是**控制流**不是数值：`ASSERT_CONTINUE` 的循环该跳过 i==5 并跑满 10 次，`ASSERT_BREAK` 的该在 i==5 停住，`ASSERT_NOEFFECT` 的该跑满 10 次什么都不发生，`ASSERT_RETVAL(false, -1)` 该返回 -1。循环条件故意用 `i != 5` 制造失败，所以这份用例本身就会触发一串断言。

## tests/CMakeLists.txt

从空文件变成一套自动收用例的规则：

- `file(GLOB ... CONFIGURE_DEPENDS)` 收本目录的 `*.cpp` / `*.cc` / `*.cxx`。这里是非递归，跟 pans 那边的 `GLOB_RECURSE` 区别开——测试只放一层。收完 `list(SORT)` 定死顺序
- 一个源文件对应一个可执行文件，目标名取文件名词干，`test_macros.cpp` → `test_macros`
- 建 target 前先查重名，撞了就 `FATAL_ERROR`，免得两个同名用例互相覆盖
- 输出统一指到源码树的 `bin/tests`，不留在 build 里
- 多配置生成器会给可执行文件自动追加 `Debug/`、`Release/` 子目录，所以额外把每个 `RUNTIME_OUTPUT_DIRECTORY_<CONFIG>` 也设成同一路径，保证各配置输出一致
- 最后 `add_test` 注册进 CTest

链接 `pans` 加 `Threads::Threads`。`find_package(Threads REQUIRED)` 现在还用不上，是给后面的多线程部分备的。

这里能看出 pans 那头 PUBLIC/PRIVATE 的设计确实生效了：测试继承了 pans 的 PUBLIC 依赖，拿到了 `-I.../pans/include` 和 `pans_options` 的全部告警选项；但没有 `-I.../pans/src`（那是 PRIVATE），也没有 `-Werror`（只加在 pans 自己身上）。实际编译命令确认了这点。

## .gitignore

只加了一行 `.vscode/`，把编辑器目录挡在版本控制外。工作区里的 `.vscode/compile_commands.json` 是手工放进去的编译数据库，内容是 Debug 配置的快照、路径为绝对路径，跟着 `build/`、`bin/`、`lib` 一样不入库。

## 实测

当前构建目录是 Debug（`-DPANS_DEBUG`，无 `NDEBUG`），`bin/tests/test_macros` 的编译时间晚于两个源文件，是当前代码的产物。

- `ctest`：1/1 **失败**，报 Subprocess aborted
- 直接跑：打印 "compiled in debug mode"，循环输出到 `AAA----- 4`，然后在 `ASSERT_CONTINUE` 那一行终止，退出码 134（SIGABRT）。stderr 上两条信息，一条是 `PANS_ASSERT` 自己打的 `test_macros.cpp:63ASSERTION FAILED: i != never_reached_condition`，另一条是 libc 打的断言失败
- 也就是说执行根本没走到后面几类宏，第一个失败的断言就把进程带走了

构建目录早先是 Release，同一份代码当时跑的结果完全不同：退出码 0，stderr 上 8 条断言诊断，控制流全部走完（CONTINUE 的循环跳过 i==5 跑满 10 次，BREAK 的停在 i==5，NOEFFECT 的跑满 10 次，`ASSERT_RETVAL(false, -1)` 返回 -1），`ctest` 1/1 通过。

两次合起来说明一件事：**这个用例的通过与否完全由构建类型决定**。Release 下 `NDEBUG` 让 `assert` 变成空操作，宏失败只打印然后继续，退出码恒为 0，所以必然通过；Debug 下 `assert(x)` 生效，第一个失败的断言就终止进程，所以必然失败。用例验的那套控制流在 Debug 下其实一行都没验到。

## 遗留

- Debug 构建下这个用例是红的，且失败点在最前面，后面的宏都没被覆盖到
- `pans/pans.not.empty.file.cpp` 还在，`macros.h` 是纯头文件，pans 库里仍然没有真实实现
- `PANS_ASSERT` 的诊断打印没跟 `NDEBUG` 联动，Release 下会继续刷 stderr
- `PANS_ASSERT` 和 `PANS_ASSERT2` 的输出格式不一致
- `INVALID*` / `MAX_U*` 的 64 位版本用 `~0ULL`，其余用字面量，类型不统一
- `Threads::Threads` 已链接但还没用上
